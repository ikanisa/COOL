# Collect MVP — remaining work to go live

This is the minimum launch path established by the source review so far. It is a working list, not a production approval: the semantic file-by-file review is still incomplete, and local synthetic tests do not prove a deployed service, provider delivery or device behavior. Detailed findings, evidence and scope are in the [source audit](mvp-source-audit-20261104.md).

## Product decisions already made

- Launch the existing Android and iOS apps as updates, with the Admin panel, self-hosted Supabase and local SMS services. The owner reports the earlier mobile versions were approved; current store identities and signing still need verification.
- Historical data is not required for the first launch. Use one authoritative fresh production database and writer.
- Members authenticate by SMS OTP, with optional Collect-managed face enrollment and remote matching through OpenFace. SMS OTP remains the alternative when face is not used.
- A member's saved MoMo number may differ from the phone number used to sign in.
- An eligible member can create a private group automatically. Its receiving account is the creator's saved MoMo account at creation; later profile changes must not silently redirect an existing group. Admin manages public groups and handles exceptions. Routine private-group creation and eligible transaction credit do not require manual Admin approval.
- Members do not select or manually upload SMS. Android member capture remains enabled when the member grants access; the separate gateway-upload hold and outbound receipt-dispatch hold remain in place until qualified.
- Reject animated images with a clear message while accepting supported static files. APNG decoding and a decoder supervisor are not launch requirements.

## Remaining launch tasks

1. **Seal the local production environment.** Select an exact source revision, build and self-hosted configuration; install the reviewed schema on a fresh database; configure protected secrets, certificates, reachable mobile/Admin origins, persistent storage and one financial writer. Prove service readiness and monitoring from the actual deployed environment. The code and local test profiles do not establish a running production deployment.
2. **Complete and qualify SMS OTP.** Connect registration and existing-member login to the selected local SMS sender, and verify delivery, expiry and normal wrong-code handling on real phones. Implement safe handling for a verification response that is lost or overlaps another attempt, and preserve a same-session path to complete the member profile without replaying a consumed OTP. Prevent account/session switches and router transitions from reviving stale profiles or stranding users. Enable and qualify the chosen registration, CAPTCHA and other required deployment settings.
3. **Integrate optional OpenFace.** Capture enrollment images with the member's consent, bind enrollment to the Collect account, and connect fresh remote face matching to a trusted, revocable Collect session bridge. Qualify facial-data protection, model and presentation-attack controls, failure/recovery behavior, and both mobile platforms. The separate OpenFace source is not yet a Collect integration.
4. **Finish the member MoMo profile.** Support a MoMo number that may differ from the sign-in phone, its provider, optional code and the requested distinct MoMo account name across member and Admin contracts. Replace the current same-number restriction with a separately qualified MoMo-number verification and account-association flow; qualify updates, concurrent changes and current-session readback. Bind contribution sender and private-group receiver snapshots to the applicable association rather than an inferred or mutable number. A phone OTP by itself is not proof of a provider wallet name or merchant-code ownership.
5. **Finish automatic private-group creation.** Create the group, invitation and owner membership atomically with a snapshot of the creator's saved receiving account. Keep existing client contracts compatible, and retain the exact request identity, account expectation and body through a lost response or restart; reconcile an unknown result instead of creating a replacement blindly. Verify the current group and membership before presenting success. Qualify profile/session changes, duplicates and real PostgreSQL concurrency. The current ordinary creation path stores no receiving account.
6. **Complete group discovery and membership.** Provision the real BuriMunsi public group and authorized receiving route; let users discover and join it without contributing. A join-only action is now present on public group details; qualify its real sign-in return, widget behavior, retry and server readback. Qualify other public groups and private invitations, eligible automatic membership, removed-member policy, current member lists and the existing list-size limits. Admin needs the authorized public-group create/edit and exception journeys. Do not rerun the previously flagged roster action.
7. **Qualify the MoMo USSD handoff.** Confirm the correct provider menu, recipient type, number or code, amount, cancellation and dual-SIM handling on supported Android and iOS devices. Ensure the native allow-list and app construct the same qualified request. Current source has an unresolved MTN format discrepancy, so it is not evidence that a real payment reaches the intended recipient.
8. **Implement automatic receipt-to-ledger credit.** Automatically capture and parse eligible MoMo evidence, match it to the correct member, group and transaction, and commit a single eligible credit without routine Admin review. Qualify a suitable local parser: the currently admitted unpaused extractor instead sends the retained sender and full SMS body to an external AI provider. Any explicitly chosen alternative needs accurate disclosure and qualified data handling. Add a versioned payer-side observation for outgoing recipient, amount, reference and role-bound source excerpts; that observation alone does not authorize credit. Keep ambiguous, conflicting or incomplete evidence in an exception path. Qualify duplicates, simultaneous arrivals, retries, reversals and database transaction boundaries on PostgreSQL. The current traced reconciliation route requires a distinct reviewer and is not the requested automatic flow.
9. **Complete automatic SMS evidence capture.** On Android, qualify consent, automatic detection and sending of new eligible MoMo messages, session changes, local queue custody and unattended recovery without member selection or manual upload. The current filter can also select unrelated sensitive messages, so qualify filtering and the active disclosure while preserving the owner's choice to keep member capture enabled. Establish and test an automatic evidence path for iOS contributions. Qualify the selected gateway's admission and recovery policy before removing its separate upload hold; preserve queued and unknown outcomes.
10. **Reconcile and display balances.** Bind each wallet-balance observation to the correct account and transaction, then handle missing, delayed, conflicting and out-of-order messages, fees and unrelated wallet activity. Update the appropriate member and group balances from the authorized ledger and verified observations, and show consistent results in mobile and Admin. A receiving account's SMS balance is not automatically evidence of a payer's wallet balance.
11. **Send automatic transaction confirmations.** Add a durable post-commit SMS obligation for each qualifying transaction, connect it to one authorized local sender, and include the appropriate new member/wallet and group balances when established. Provide and qualify the member's enable and withdrawal choices, including after leaving or rejoining a group, and the verified-phone proof needed after face sign-in. Qualify recipient identity, reversals, duplicate prevention and unknown send outcomes. The existing held operator-driven path does not establish automatic SMS delivery.
12. **Qualify resilience and release.** Resolve current-session and member-scope stale-data handling, exact-request recovery and protected queue limits. Qualify ordinary pending-intent resume against the originally accepted receiving route; some retained commands do not record that route, so keep recovery non-actionable when it cannot be established. Qualify encrypted backups, an independently protected restore path, and the retention, erasure and external-copy handling of SMS and facial data without retrying the flagged recovery action. Build the Android and iOS updates with the approved identities and bind their and Admin's origins, public keys and enabled channels to the exact running self-hosted release. Run real-device journeys through OTP, profile, optional face, group membership, USSD, automatic evidence, credit, balances and SMS. Verify the Admin routes, real service/provider outcomes and Android SMS permission declaration; submit the updates and verify store acceptance and distribution before cutover.

For cutover, qualified evidence admission and parsing must feed atomic credit before balances and automatic confirmations can be relied on. Implementation work can proceed in parallel.

## Work that must continue alongside launch

Complete the semantic file-by-file review of remaining active mobile, Admin, Supabase, deployment and test code. Reconcile duplicates only after checking consumers and provenance; preserve the original checkout and immutable evidence. Commit and push qualified changes to `main` while avoiding GitHub billing-dependent tasks. The task list should be revised as the review or actual deployment evidence changes.
