# Collect Full-App Revolut-Parity Goal

## Goal statement

Transform the Collect Flutter member app, its supported public web surface, and
its Admin PWA into one coherent, production-quality product system that follows
the verified Revolut reference grammar while retaining Collect's own identity,
Rwanda/MoMo domain behavior, privacy boundaries, data model, routes, and
regulated-action safeguards.

The goal is complete only when every in-scope screen and state is implemented,
the complete test and device matrix is evidenced, Product Design visual QA
passes against combined source/implementation comparisons, and the repository
has a truthful release-readiness record.

## Role

Codex operates as the Flutter implementation, Product Design fidelity, QA, and
release-hardening lead for this engagement.

## Authority

- Authorized: local source edits, local test data, local builds, simulator and
  emulator interaction, screenshot capture, accessibility checks, performance
  diagnostics, documentation, and non-destructive repository inspection.
- Authorized by this goal: implement the five-destination mobile information
  architecture, including global Contribute and Activity routes, because these
  were explicitly included in the requested remaining-task programme.
- Not authorized: production Supabase mutation, payment execution, user contact,
  credential creation, store upload/submission, public deployment, DNS changes,
  billing changes, or signing on the user's behalf.

## Non-negotiable product constraints

1. Use Inter as the exclusive runtime font family; do not use or redistribute
   the legacy proprietary reference family.
2. Match verified reference geometry, density, hierarchy, interactions, and
   state treatment without copying Revolut trademarks, proprietary copy,
   customer data, unsupported finance products, or unlicensed assets.
3. Preserve Collect's real contribution, MoMo handoff, ledger, privacy,
   authentication, offline, and recovery behavior.
4. Never expose full private receiver details outside an explicitly confirmed
   payment review context.
5. Never trigger a real payment, external submission, production mutation, or
   store release during evidence capture.
6. Do not claim full parity from narrow screenshots, targeted tests, or build
   success alone.

## Quality gates

### Gate 0 — Authority and scope

- Local implementation authority confirmed.
- Production, payment, store, and public-release actions remain prohibited
  without separate explicit approval.

### Gate 1 — Product Design evidence

- Every material redesign is grounded in an opened verified reference.
- Every final visual claim uses a combined source/implementation comparison.
- `design-qa.md` ends exactly `final result: passed`.

### Gate 2 — Architecture, data, security, and privacy

- Existing Riverpod, GoRouter, repository, and Supabase boundaries remain
  coherent.
- New routes do not duplicate ledger truth or bypass authorization.
- Payment and private receiver data remain protected.

### Gate 3 — Implementation quality

- Shared tokens/components are used instead of screen-specific hardcoding.
- Formatting and `flutter analyze` pass.
- No unexplained source-contract or regression failures remain.

### Gate 4 — Accessibility, responsive behavior, and performance

- Target-size, semantics, reading order, large-text, contrast, theme,
  reduced-motion, compact/large viewport, and platform checks pass.
- Performance evidence exists or a concrete blocker is recorded.

### Gate 5 — Release readiness

- Full automated suite and available release builds pass.
- Security, dependencies, permissions, privacy, account deletion, and store
  policy status are documented.
- External signing/store/deployment gates are clearly separated.

### Gate 6 — Closeout

- Every requirement has direct evidence.
- Every issue is closed, accepted as P3, or assigned as an external/human gate.
- The goal is not marked complete while evidence is missing or indirect.

## Definition of done

This goal is achieved only when all ten workstreams and all seven gates are
closed with current-state evidence. A passing subset, a simulator screenshot,
targeted tests, or a release build cannot substitute for this definition.
