The main release question is whether a receipt is merely **SMS observed** or can become **financially posted**. The current parser reports `awaiting_reconciliation` (`supabase/functions/parse-payment-sms/index.ts:13-18,144-155`), but the historical financial-core migration defines a service-role SMS finalizer that invokes provider finality using the SMS attestation hash (`supabase/migrations/20260903084000_hybrid_direct_ussd_financial_core.sql:1479-1556`). A new additive containment migration makes that finalizer return `awaiting_reconciliation` (`supabase/migrations/20260928160000_sms_observation_never_settles.sql:1-36`). It passed the isolated 133-migration clean replay and a guarded 127+6 synthetic historical upgrade with rollback-only SQL assertions, but is **unapplied to an authorized hosted target**. The separate staged hardening SQL also specifies await-only behavior (`deploy/hardening/receipt_security_v2.sql:1-2,50-60`). Actual deployed function definitions and execute grants decide which boundary exists in the target environment. See the [local financial evidence packet](../financial-core-2026-09-28/README.md).
