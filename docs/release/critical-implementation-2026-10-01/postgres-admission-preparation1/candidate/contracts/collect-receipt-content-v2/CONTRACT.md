# Collect receipt content policy 2

Owner authorization is the exact message recorded in the additive migration. Approval method is `user_delegated_policy_selection`; no name, independent legal review, translation review, settlement verification or sender acceptance is claimed.

Content version **2** is distinct from collection configuration version **1**. Collection policy enablement/revision and member consent/contact revisions remain required. New actual receipt snapshots use v2, default Kinyarwanda (`rw`). Explicit private renderer inputs support `rw`, `en`, `fr`; no member language preference is inferred. The template key remains `buri_munsi.payment_received`.

Receipt words describe recorded savings. The dated value is the member's immutable savings snapshot in that group at the snapshot's database recording time, shown in Africa/Kigali (CAT). The message omits the group total and makes no provider settlement or delivery claim. Amount must be positive whole RWF; member balance must be nonnegative whole RWF. References must match the existing bounded safe reference grammar. English/French are deterministic explicit helpers, not new preference settings.

Creation accepts no caller-supplied recipient, balance, message or language. It requires the existing posted Rwanda payment, matching immutable receipt journal/snapshot and one asset/debit plus one member-liability/credit line, a content-bound stored provider confirmation, current active allocated membership, an account-independent member, configured enabled active ikimina savings collection, current contact and enabled recorded consent. A stored confirmation is recorded backend evidence; it is not independently verified provider settlement. Invalid/unsupported financial evidence produces no SMS; financial posting remains deterministic and independent of Codex. An unsafe reference preserves the existing deliberate suppressed primary behavior.

The primary identity `(payment_id, template_key)` and unique snapshot remain unchanged across content versions. Installation does not rewrite, backfill, unsuppress or replace existing v1 bodies, snapshots, balances, queue state or attempts. Dispatch paused preserves newly eligible v2 queued work. New claim/send authority on v1 is refused, with new claims raising SQLSTATE `55000`, `CONTENT_POLICY_REVIEW_REQUIRED`, before claim/reset/suppression writes. Earlier armed attempt outcome reconciliation remains available through the existing immutable observed-outcome function, including while the dispatch flag is off. Unknown means manual evidence review; no blind retry, correction, resend or historical automatic catch-up is approved.

Existing `admin_list_hybrid_sms_receipts`, `admin_get_hybrid_sms_receipt`, and `admin_get_collect_investigation_v1` keep their JSON keys and permissions. The fixed template key's `template_version` accepts only integer **1 or 2**. Legacy masked previews use the legacy renderer; v2 previews use the dated member-only renderer and opaque snapshot alias. Admin financial fields retain their existing privileged read access; outbound member messages omit group balances.

New authenticated `admin_receipt_content_policy_v1()` returns the exact JSON schema here. It uses locked current email-owner authority and existing payment/notification/system-health reads, with a 100 ms authority lock timeout (`55P03`, `receipt_policy_authority_busy`). A fresh read is 60 seconds from `checked_at`; this is the read TTL, not provider/source freshness. Private schema tables/helpers have RLS and no direct API-role access. The public read does not expose original contact, body, balances, reference, owner message, actor/session or approval person.

This migration authorizes receipt content and disclosure mechanics only. It does not enable the SMS flag, provision a sender, issue a dispatch grant, select operating caps/modes/schedules, or implement run-bound event handling. Historical catch-up/correction/resend and live gateway/run/pilot authority remain closed until separate implemented, reviewed contracts exist.
