# ARC-10 read-only resolver contract and consumer plan

This change implements a reader only. The existing exact 98-object manifest and all original reports, commands, indexes, helpers, backup/restore implementations and caches remain unchanged. No archive, restoration, engine installation, key generation, storage transfer, source promotion or removal is authorized or performed by this reader.

The public Python API will load an explicitly hash-pinned **out-of-band trust document**, not derive authority from the relocation catalog. Its expected inputs include exact source repository/epoch/manifest identity, encrypted repository ID, full snapshot ID, engine identity, protected separately verified restored-root filesystem identity, pinned immutable catalog, two independently verified file-cohort receipts, their native receipt artifacts, and selected original source/index anchors. Every artifact has an exact expected whole-file digest and size. No receipt is selected by basename, newest date, partial snapshot ID or global discovery.

The immutable catalog maps unique exact original relative paths to unique exact snapshot-relative paths, preserving each whole SHA-256, logical size, file mode and original mtime. Global source repository/epoch/manifest, encrypted repository and full snapshot identities must match the external trust document and both receipts. The independent restore receipt must cover the entire same catalog and bind the exact restored directory path/device/inode/mode, native restore receipt and verified engine-check receipt. Catalog/receipt schemas are strictly versioned; unknown keys, duplicate JSON keys/rows, missing/failed/partial scope and inconsistent identities deny resolution. There is no circular self-hash: the external trust document pins the catalog and receipts; the catalog does not pin its own receipt.

The implemented engine-input schema requires the boolean `encrypted_repository_verified: true` as well as `full_data_integrity: true`. These are independently verified input facts whose complete receipt bytes the caller must explicitly pin; this reader cannot establish either fact from flags or from a native receipt hash alone. The final observation fence reopens each selected file with the same descriptor guards and checks its full device/inode/mode/size/mtime/ctime/link-count fingerprint after the metadata checks. It catches source appearance/disappearance and late replacements without returning an unchecked path or rehashing the full cohort a second time. Observations are bounded point-in-time reads, not a global atomic filesystem snapshot.

`EvidenceResolver.from_pinned_config(path, sha256)` will construct the reader. `read_bytes(reference)` returns only immutable verified bytes, never a path for an unchecked later reopen. `verify_reference(reference)` and `verify_many(references)` return metadata-only byte-identity observations. A reference supplies the original path, digest and exact epoch; the caller retains the original dated index. The JSON CLI verifies one reference and returns fixed denial codes or bounded metadata, never payload bodies or raw operating-system errors. Explicit catalog/receipt hashes are a trust boundary: the resolver validates the relationship and local bytes, while the authorized independent verifier must first establish genuine engine and restoration acceptance.

Descriptor-relative reads with `O_NOFOLLOW`, `O_DIRECTORY` and regular-file `fstat` will reject symlink components, hardlink aliases, traversal, path replacements, changed bytes/mode/mtime, missing/tampered metadata and payloads, wrong restored-root identity, wrong repository/snapshot/epoch, duplicate requests and source/index drift. Metadata bytes, objects, paths, per-file bytes, aggregate bytes and local-read time are bounded. Original source, if still present, must match catalog bytes/mode/mtime; absence can resolve only through the fully pinned verified restore inputs. There is no original-file success shortcut, automatic network/engine invocation, implicit mount, empty stub or symlink fallback. Physical filesystem stalls remain a caller process-deadline concern; an in-process deadline is checked between local reads.

Current maintained recovery tools are specifically **database/vault** capture and PostgreSQL restore readers. Their native receipts preserve exact source contracts, encrypted remount hashes and catalog/row acceptance within that scope; they cannot attest these 98 compiler-cache files. The new reader must reject their raw formats for a file-cohort request. The normalized verified-input contract is for a future owner-selected maintained engine and independent file-cohort verifier, preserving their hash-bound native receipts. The reader does not create those receipts or treat unit fixtures as restoration evidence. [Restic's official repository/snapshot identities](https://restic.readthedocs.io/en/stable/100_references.html), [full-data integrity verification](https://restic.readthedocs.io/en/stable/045_working_with_repos.html), [Python descriptor-relative operations](https://docs.python.org/3/library/os.html).

First-batch integration will be a separately assigned caller which supplies all 98 exact references from `first-batch-candidate-manifest.json`, plus the immutable `verification.json` tree-command anchors at original lines 70 and 213. It must resolve each descendant, not rewrite those historical commands or rerun compilation against archived caches. The two existing command-tree links and all 98 incoming mappings stay unresolved until real approved catalog/engine/independent-restore inputs exist. Original Firebase source comparator, compiler logs/dependencies/object and every sibling remain preserved.

The nine consumer groups in the existing repair matrix need distinct future ownership: concise public contracts remain intact; before-source manifests, native helpers, Admin synthetic fixtures, runtime-control contracts and historical SQL/seed metadata require exact provenance and genuine affected tests before any promotion. Store/release readers can adopt this API only under separate integration ownership, preserving open release gates. This patch changes none of those consumers and proves no archive-independent build, sensitivity/retention approval, second copy, key recovery or removal authority.
