The proposed policy is a closed, bounded technical representation of a separately approved record, with whole JSON SHA256 pinned independently in server configuration. It binds a purpose, explicit enabled/approved state, approval ID and evidence digest, actual approval window, provider, exact organization/project/model/Responses endpoint, region/retention evidence references, and decoder processor/region/retention references plus exact endpoint/build. Canonical compact JSON avoids ambiguous duplicate fields. Calendar validity, real booleans, byte bounds and exact tuple matches are enforced; failure is the existing safe `roster_extraction_unavailable` HTTP503. No configuration, key, source bytes, evidence references or policy body is reflected into a public error or log.

The proposed minimum supports only the current fixed global OpenAI endpoint. It does not select a region, claim that global routing satisfies a regional requirement, or invent a regional endpoint. Organization/project headers make request usage scope explicit for the documented selection cases; actual account/key membership still needs vendor/owner evidence. Official OpenAI authentication documentation describes those headers and recommends pinned model versions plus evaluations for consistent prompting behavior. A matching model string alone cannot freeze a moving alias or establish model capability/accuracy. [OpenAI API Authentication and compatibility](https://developers.openai.com/api/reference/overview).

The recommended placement checks policy before any reservation for every PDF/image AI upload request. This deliberately returns safe503 for upload replay after approval is missing/disabled/expired, even if a historical result exists. Old rows are preserved and separate guarded recovery/read APIs are outside this change. With active matching approval, completed and failed upload replay continue to return only the original immutable outcome without redispatch. An alternative gate only when `budget.state === reserved`, immediately before decoding, would preserve cached replay while current policy is unavailable; however, denied new requests would already have consumed the existing charged reservation. Root should select this placement explicitly before implementation. Neither alternative justifies refunding/retrying an uncertain attempt or rewriting old results.

The minimum write boundary would be a new isolated `roster_ai_dispatch_policy.ts` validator, the existing runtime adapter and handler. Tests would add strict validator cases, synthetic approval configuration to current PDF/image fixtures, and real handler effect-order/held-boundary assertions while preserving the 109 current affected regressions and filename assertions. `test-plan.json` defines 23 planned scenario groups: absent/malformed/disabled/expired/unapproved policy, hash/tuple/model/endpoint/decoder/evidence mismatches, caller injection, expiry/revocation while reserve or source ACK is held, matching success, unchanged deterministic and real decoder paths, completed/failed/in-progress replay, Auth/receipt failures, unavailable key, and bounded provider failures. First run new denials against the exact old production source and preserve the expected failures; no existing mock-only success should be reused as approval-gate acceptance.

Approval validity must be rechecked at each actual external call after awaits, against the same immutable request policy/configuration. Otherwise a policy can expire or change during decoding or source ACK and a later provider call still uses stale authorization. Reread the configuration immediately before dispatch and reject changes to the pinned policy/approved tuple or credentials/signing secret, rather than continuing with an earlier mutable config object. This checks the configuration visible to that isolate; it is not a distributed instantaneous revocation mechanism or proof of live vendor retention/residency controls.
