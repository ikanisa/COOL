## Why the mapper retains gaps

The mapper recognizes only active literal function definitions (`collect_schema_domain_map.py:423-450`) and explicit top-level signature-bound static rename/schema moves (`:289-370`). Anonymous `DO`, top-level `EXECUTE` or `CALL` produces an uncertainty fence (`:372-406`); `drop-all` clears tracked state. The build uses both unfenced and fenced lineage, withdrawing candidate matches when intervening effects cannot be proved (`:573-599`). Same-body functions under another name are recorded solely as candidates (`:409-421`). Current tests deliberately preserve generated-wrapper and patched-body uncertainty (`scripts/tests/collect_schema_domain_map_test.py:337-351`), and same-body/overload/final-hash rules at 310-335.

For example, receipt-operations migration `:91-99` has a table-security/trigger loop before the static legacy policy rename. Roster recovery has anonymous trigger installation at `:466-474` and generated wrappers at `:490-548`. Later migrations contain more anonymous effects. Source inspection can identify the intended local effects, but the current mapper does not prove the anonymous blocks' full function effects or catalog prestate. The two static rename gaps therefore remain uncertainty, not evidence that the functions were actually changed or dropped.

There is no application name in this set for which this bounded review found no source transformation candidate. Actual source provenance remains unproved for all 36 in the unchanged captured map. The distinction is between an identifiable candidate operation and a closed, byte-bound execution/identity chain. Platform gaps, other catalog/caller mappings and broad ownership history are outside this review.
