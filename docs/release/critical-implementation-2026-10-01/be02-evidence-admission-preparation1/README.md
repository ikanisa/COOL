# BE-02 evidence admission preparation

Status: proposed, route undecided, not installed or executed. Only this preparation directory was written. No database, Docker, provider, device, registration or maintained application changes were made. No source object, approval, settlement result or retention authorization has been created.

The required outcome is that new financial posting cannot depend only on a typed evidence hash and two approvals. A retained, authenticated or explicitly constrained internal source must be admitted under the actual finance/security decision, matched to the candidate and independently reviewed. Existing authorization, immutable journals, compensating reversals and truthful historical acknowledgements should be preserved.

## Route decision remains outstanding

The owner question offers authenticated provider API, independently authenticated provider/bank statement, or a constrained internal reconciliation policy. None is selected here. A statement route does not add bank payment rails; current admitted payments remain Rwanda/RWF/MTN MoMo/Airtel Money unless the owner separately changes product scope.

The actual decision must identify who may authenticate/import the evidence; how provider/statement origin, receiver account authority and source bytes are verified; permitted financial status; time matching/tolerance; ambiguous/mismatched handling; correction/reversal reasons; and the precise evidence level that receipts and Admin may claim. An internal policy may authorize internal ledger reconciliation while keeping `provider_settlement_verified=false`. A hash, object locator, arbitrary signature string or maker/checker identity cannot alone prove provider authenticity.

Retention/custody also remains undecided: approved private storage boundary and version immutability, retention/hold/deletion treatment for original statement/provider bytes and derivatives, restricted reveal/export authority, and actual byte readback. This proposal does not pick a period, location or legal retention basis and does not alter BE-05's separate retention workflow.

## Proposed implementation boundaries

`proposed-schema.sql` is a concrete additive schema and private assertion helper, not an installable complete release. It inserts no approval or evidence rows, grants no API role source-write/admission authority and does not replace any maintained function. Its object-registration helper computes hash/size from bytes supplied by the future trusted adapter; it does not authenticate those bytes or establish that the referenced object is durably retained. The selected adapter must do those operations before invoking it. Its source-record digest is generated in SQL from the normalized bound tuple. Its private assertion compares retained source data with the existing review and current locked payment, including currency/time/reference, unique candidate and approved policy. The retained object/checker provenance references are custody facts only after the selected adapter verifies them.

Implement the following coherent maintained slice after route selection:

1. Add one new migration with the reviewed additive tables/helpers and replacements of the existing proposal, approval, authorization and finalizer. Do not modify applied migration history. Register no invented policy approval; actual owner/finance/security authority must be recorded through its selected trusted administrative boundary.
2. Keep `propose_payment_reconciliation_v2`'s signature. Resolve its normalized hash/reference/time to exactly one usable retained source record; reject zero/multiple results; compute/compare current fingerprint under the existing locks and insert an immutable review binding in the same transaction as a new review. A typed hash remains a selector/claim, not evidence. Existing unconsumed reviews have no binding: require a fresh proposal and independent approval; do not attach source facts to an old approval after the fact. A new explicit-source-ID v3 proposal can be introduced only if the selected adapter/consumer requires it; it is not necessary for the v2 compatibility path.
3. In approval, keep current actor/session/expiry checks. Under the existing payment lock assert source admission and current policy before recording the checker. Record the source-record ID/digest, source byte/provenance hashes, policy ID/rules hash and custody authorization hash in the existing audit metadata. The checker sees retained source/custody and matching facts through a restricted read API, not just a hash. Require the existing current AAL2 reconciliation actor for sensitive source metadata; ordinary list readers receive redacted admission state. Do not expose private object locators in these responses.
4. In the finalizer, preserve the existing session/roster/review/payment lock order. Preserve the consumed-review replay branch before any requirement for newly added source metadata; do not invent historical approvals, object references or settlement labels. For a new posting, assert the bound source immediately before `process_provider_finality_event`, keep the assertion locks until commit and insert the unique consumption in the same transaction after successful posting. A consumed genuine source row cannot fund another payment. Policy revocation and source admission must use the same policy/source advisory lock order, so a winning revocation denies new posting and a completed permitted posting keeps truthful history.
5. Keep the strict five-key finalization v2 response and its current `independently_reconciled` value as an internal ledger acknowledgement where compatible. Expose the actual selected evidence level and `provider_settlement_verified` in a separate versioned source inspection response; never infer it from that v2 label. Preserve `replayed=true` and actual `posted`/`reversed` status for consumed reviews. Use the existing safe public error mapping; source denial under SQLSTATE `22023` becomes `reconciliation_conflict`, with no private object/provenance details echoed.
6. Extend `AdminRepository`/`SupabaseAdminRepository` and the existing reconciliation page with source inspection/selection. The existing proposal can use the server's admitted source-record reference and computed hash. Replace format-only 'verified hash' wording with the actual evidence state; show internal-policy limits, source record, time/amount/currency/network/receiver/transaction comparison and policy/checker provenance. Retained bytes need a separately audited, authorized reveal/export path. Keep existing session fencing, permission checks, no automatic write retries and Revolut components/tokens. No new appearance authority is proposed.
7. Preserve `admin_reverse_momo_payment`'s current signature and compensating mechanics. For a fresh operation, resolve its existing request ID to a private, immutable operation binding containing the selected policy, admitted reversal evidence, payment fingerprint, actor/checker decision and reason. Assert that binding before compensation; insert correction lineage in the same transaction only after the real reversal journal exists. Preserve its original exact request replay branch. A replacement payment requires fresh admitted receipt evidence and links back to the actual original and reversal journals; never rewrite original balances/journals or automatically resend receipts. The selected policy must define who may approve a reversal/internal correction; this proposal does not fabricate that authority. Existing permission-only reversal cannot serve as external reversal evidence.

## Completion requirements and present limits

The schema/guard draft is unexecuted and lacks the selected trusted adapter and maintained caller replacements. Its generic assertion proves equality with admitted records, not origin authenticity or actual enforcement of the policy's referenced time/custody rule; the selected adapter must enforce those rules and bind its approved checker version/hash. Source-record status is accepted only under explicitly recorded permitted states, and nonsettled/unknown/reversed receipt evidence never authorizes new receipt posting. It must be reviewed against the current ordinary-owner effective schema before installation. `consumer-test-plan.md` specifies actual consumer positive/denial cases; none has been run for this proposal. Source hashes in `source-binding.json` bind the observed inputs, not deployment/provider/security acceptance. `proposal-seal.json` and `SHA256SUMS` bind only the preparation files. Actual route/custody authorization and genuine provider/statement acceptance remain required facts; this package cannot mark BE-02 complete.
