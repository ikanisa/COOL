This packet prepares a private default-deny AI dispatch implementation for BE13-L04. It has not been promoted into the maintained checkout, deployed, or activated. All 22 current maintained input hashes remained unchanged throughout the private work. Root must review the complete seven-file diff before authorizing promotion. No processor, project, region, retention or owner approval was selected; every success record is clearly synthetic test data.

The production proposal adds a bounded, closed 20-field server approval record with a separately configured whole-JSON SHA256 pin, exact organization/project/model/endpoint and decoder endpoint/build bindings, purpose, real enabled/approved values, calendar-valid approval window, approval ID/evidence digest and required processor/region/retention evidence references. These are technical representation checks. A syntactically valid reference or digest cannot prove its underlying legal, vendor or owner acceptance.

The handler takes one immutable snapshot of its nine effective configuration values. It validates the policy SHA before its final current-time check, then synchronously compares fresh configuration before reservation. For an AI PDF/image it repeats that comparison inside the actual decoder fetch wrapper after the awaited HMAC has finished. It also repeats it directly before OpenAI fetch after source acknowledgement and request-body construction. No await occurs between either final fresh configuration/time check and actual fetch entry. The decoder adapter's existing sanitized transport error behavior is retained; a local marker preserves the existing safe extraction-unavailable code specifically when the approval guard denied dispatch.

Root explicitly reviewed the comparison boundary: existing runtime model/API-key/decoderURL trim/default normalization stays in place. Exact effective `configuration()` values are compared, rather than underlying environment whitespace that the adapter already normalizes. Policy JSON/hash, organization/project, decoder build and signing secret are untrimmed. The snapshot detects changes to all nine effective fields and rechecks the same approval window. No extra secret serialization, network policy lookup, or new normalization rule is added.

Absent, disabled, unapproved, malformed, expired or mismatched approval returns the existing generic `roster_extraction_unavailable` HTTP503 before resource reservation, decoder transfer or provider transfer. A policy/configuration denial after reservation uses the existing terminal failed-charge path. Once OpenAI fetch may have left the process, transport uncertainty remains ambiguous, charged and unretried. An approved completed replay remains immutable; a newly submitted AI upload/replay after approval revocation is denied before a new reservation. Historical guarded recovery and deterministic text/CSV/TXT/XLSX behavior remain unchanged.

OpenAI requests retain the fixed global Responses endpoint, original PDF/image bytes and MIME, model, strict schema, developer instruction, `store:false`, no tools, output limit, timeout/redirect controls and generic `collect-roster.pdf` filename. Two validated request headers select the represented organization/project. Their presence does not establish actual key/project membership, residency or retention. SQL `p_ai_metadata` remains the exact existing three-key provider/model/prompt-version contract. Durable attempt-policy lineage is still missing and requires a separate versioned SQL/receipt change.
