# ARC-07 — Admin PWA delivery batch

The current worker and build postprocessor now keep each open Admin tab on its installed static build. A new worker precaches and waits until every previously controlled Admin tab/window closes. Production does not force activation, claim an already loaded page, reload unfinished operator work, or remove browser account/draft storage. Ordinary reload while another old tab remains open continues using the old worker and shell.

The postprocessor emits runtime files under `_build/<SHA-256>/` and configures Flutter's entrypoint, asset and CanvasKit bases accordingly. The shell font/favicon and manifest icon use that namespace. Stable compatibility paths require HTTP revalidation; only content-versioned runtime paths are immutable. This bypasses an existing browser's old one-year immutable main/assets cache without clearing that cache or user state. The worker checks all precache response hashes, waits for every concurrent write before deleting a rejected installation, and returns an uncached HTTP503 if an installed static resource is missing rather than combining releases.

The canonical machine receipt is [pwa-batch1.json](pwa-batch1.json). It binds all 14 changed implementation/consumer files, the final real browser report, negative served-resource/header receipts and logs. Current production gates and the three existing browser lifecycle consumers were adapted to the same policy. Earlier passing browser attempts remain in the task cache; attempt3 covers the final source after the idempotence fix.

## Observed verification

- Real Chrome 154.0.8037.59 on loopback: 28 checks passed, with all 13 browser input hashes stable. Two tiny fixture releases changed both main and lazy asset bytes. The browser retained a deliberately populated old immutable HTTP cache yet loaded the new namespaced runtime. Two pending fixture tabs stayed on their old main/assets while the new worker waited; closing every scoped tab allowed activation and only then old owned-cache deletion.
- Real browser mixed-byte and interrupted-install failures retained the active build and removed the partial new cache. Offline reload used a complete installed static build and could not fetch private account state. Cookie changes produced fresh private responses, which never entered the static cache. Rollback waited for open newer-version tabs and restored matching older main/assets after those tabs closed. No provider or real account was used.
- Loopback served gates passed the expected contract, rejected a versioned resource whose bytes differed from its worker hash, and rejected a stable main bundle served with the retired immutable policy. The live gate samples main, icon and one Flutter asset; it is not a full deployed-object attestation.
- The actual dated `build/web` Admin artifact was copied into the task cache and adapted through the current bootstrap/postprocessor. Its real compiled Flutter loader, CanvasKit/fonts and Admin login rendered from versioned assets in Chrome, with HTTPS requests blocked for this probe. This proves loader integration on those captured bytes; it does not prove a fresh current-Dart Admin build, authenticated business actions or visual fidelity.
- The 27 affected Dart consumer tests passed. The worker VM boundary/integrity/cleanup checks passed; those mocks are not the browser lifecycle proof. The two existing Ruby bundle-gate tests passed nine assertions. Bash/Node syntax and affected diff checks passed. Postprocessing an already processed fixture was byte-for-byte idempotent across 13 files.

## Release operation and remaining acceptance

Operators must finish or save pending work and close **every** Admin browser tab and installed Admin window before reopening to receive an installed update. Releases must retain backend API compatibility for the older tabs that remain open. Failed or partial static publication must be corrected before the new worker can install; an evicted static build requires closing all Admin tabs and reopening online. The QA helper which navigates tabs away and back is test-only and is never called by production.

ARC-07 remains open for its original full acceptance: two reviewed real hosted Admin builds must prove exact resource hashes, first visit, actual installed PWA warm update, authenticated pending operator tasks and multiple tabs, interrupted installation, offline and rollback. A fresh immutable current-source app build, installed OS PWA lifecycle, device/browser matrix and the live hosting/CDN/atomic publication contract remain unverified. There was no real deployment, production-profile change, provider call or deletion of user state in this batch.

## Primary references

Flutter documents the accepted [loader base options and configuration forwarding](https://docs.flutter.dev/platform-integration/web/initialization). The installed SDK's loader/type declarations were also inspected; the actual compiled-artifact browser probe verifies the integration described above. Chrome documents the [service worker waiting and client lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle). The [skipWaiting](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/skipWaiting) and [claim](https://developer.mozilla.org/en-US/docs/Web/API/Clients/claim) APIs force the takeover removed here. [Registration updateViaCache](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register) and [Cache-Control semantics](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control) support the worker-update and mutable/versioned header split. These sources describe platform behavior; the local browser evidence establishes only the observed scope above.
