## Requirements and external decisions

They classify phone hashes as personal pseudonymous identifiers, leave raw-body erasure unimplemented, and require copy/processor/hold treatment. The unkeyed normalized-phone digest is dictionary-matchable. It cannot be called anonymization.

Rwanda Article 23 makes erasure conditional and recognizes specified exceptions. It also requires notice to third parties about copy/link erasure requests and a written/electronic response about erasure within 30 days. Individual exemptions and operational decisions still need a documented basis. [Official DPO rights text](https://dpo.gov.rw/dpp-law/rights-of-the-data-subject).

Articles 48–52 address overseas sharing/contracts, authorized overseas storage, purpose-based retention and destruction preventing intelligible reconstruction at the end of retention. They do not supply one universal financial horizon for this product. Bind the actual registration, hosting and transfer decisions before production processing. [Official DPO retention and transfer text](https://dpo.gov.rw/dpp-law/sharing-transferstorage-and-retention-of-personal-data).

Auth removal invalidates refresh/session state, but an issued JWT can still be accepted until expiry where no live-session check is performed. Storage ownership can prevent removal. An application flag or temporary ban alone is insufficient. Local config uses a one-hour JWT expiry; hosted parity is unknown. [Supabase official user management](https://supabase.com/docs/guides/auth/managing-user-data).

OpenAI distinguishes application state from abuse-monitoring logs. Default content-containing logs can be retained up to 30 days with stated exceptions; ZDR/MAM require approval and actual project configuration. `store:false` does not prove those controls, and flagged image/file safety review has exceptions. No processor-account setting was inspected. [OpenAI official data controls](https://developers.openai.com/api/docs/guides/your-data).

The approved per-class schedule, retention/hold decisions, processing contracts, hosting/transfer registration, provider retention settings, backup overwrite policy and responsible operational owners remain missing inputs. Safe intake, verification and access restriction can be implemented while destructive phases refuse missing policy. This packet invents no duration, approval or external confirmation.

## Concrete implementation boundary and lifecycle

### 1. Intake, scope and replay

Introduce a private privacy module and a versioned request API. Persist request UUID, verified principal, request kind, explicit scope, canonical scope hash, policy version, verification references, expected revision and timestamps. Bound reason codes and optional free text at the server. Return a stable request receipt to the app/support workflow. An identical request UUID/payload replays the same receipt; a changed payload conflicts. An active equivalent scope reuses or explicitly relates to the existing request. Concurrent overlapping requests serialize by subject/scope and share disposition facts rather than performing two independent destructive passes.

Self-service derives its principal from a verified live Auth/session, never a submitted user ID. Assisted support verifies the subject through a defined process and stores a proof reference, rather than attaching unbounded identity documents to audit logs. Exact receipt-only, imported-member, and full account scopes need distinct eligibility. A receipt may describe a payer as well as a receiver; an import actor is not every roster data subject. Build a verified subject-to-field/asset map with stable member/payment/import identifiers. Ambiguous names, last-three digits or unverifiable hash matches require governed review and must not authorize destructive matching.

Keep the legacy request interface as a bounded compatibility adapter until clients consume the versioned receipt; preserve request history rather than falsely relabeling old pending requests complete. The website currently offers contact guidance, so assisted requests need the same controlled intake/status path.

### 2. Separate the retained principal from live Auth

Recommended schema direction: retain a minimal stable principal record and make its live Auth association independently nullable/removable. Existing profile UUIDs and six-digit Collect IDs should keep stable financial meaning; a new nullable `auth_user_id` link or an equivalent private association can model active authentication. Do not make the primary-key profile ID nullable or solve the problem with an uncontrolled CASCADE.

Before adopting this direction, bind all effective `pg_constraint`, `pg_trigger`, `pg_policy`, function/alias ACL, view and grant definitions from the current full chain. Migrate the original profile/Auth dependency and the four direct `collect_ops` Auth references to the retained principal while preserving recipient/history invariants. Review every profile RESTRICT/SET NULL/CASCADE consumer, registration trigger, member linkage and ID reservation. Explicitly unlink eligible live member associations; a retained profile means previous ON DELETE SET NULL behavior will not run automatically. Clear eligible profile/contact/avatar/member fields only under policy, and refuse to overwrite constraints with invented identities that could become payment destinations.

Install a server-owned restricted/deleted state and actual live-session/identity checks in every affected RLS, RPC, Edge and Storage path before allowing Auth removal. A retained profile plus a stale `auth.uid()` token must not retain ordinary access. Privileged disclosure, audit and servicing access stays capability-scoped. Use the supported Auth administration API from a dedicated server executor after Storage/FK preconditions; no client-held service credential or direct production SQL deletion. This is a cross-schema migration, not a small account flag.

### 3. Policy and legal holds

Create a versioned per-class policy registry: purpose, lawful retention basis, trigger, permitted action/fields, horizon only when actually approved, approving authority/evidence, processor/copy scope, and review/expiry rule. Record specific legal holds with scope, basis, authority, start/end/review evidence and audited release. Preserve the existing operational recovery TTL independently of legal retention.

The executor locks and rechecks the request, policy revision, field scope and active holds immediately before each mutation. Unknown basis or missing horizon blocks that destructive phase. A hold on one record does not silently prevent all eligible unrelated actions; the manifest records each retained disposition and reason. No inferred blanket exemption for every financial-adjacent field is allowed.

### 4. Durable plan, restriction and bounded execution

Materialize a private manifest of exact database fields/rows, lineage descendants, device stores, objects/versions, exports, backups, processors and uncertain transmissions. Record each item's class, stable key, original version/hash, planned action, hold/policy decision and resulting receipt. Minimize this manifest: do not copy raw bodies or whole documents into a second permanent audit store.

Use explicit phases: accepted → identity verified → ordinary access restricted → policy/hold evaluated → plan frozen → eligible database changes → external/device/copy dispositions → verification → scoped completion. Pending external evidence stays `external_pending`; unresolved decisions stay blocked with a reason. A verified completion with justified retention must list retained classes/bases and distinguish them from confirmed eligible erasure. Never derive completion from elapsed time or a provider request acknowledgement.

Claims require a lease/fence and expected revision. Execute bounded table batches with SKIP LOCKED, statement/time/resource limits, per-item checkpoints and attempt receipts. Define the actual bounds in the contract and measure them; no unlimited loop. Restart after a crash, lost acknowledgement or expired lease from durable receipts, without repeating irreversible external actions. Recheck resource version/holds and fail on drift. Fix lock order with existing session/authority/source locks, and quiesce parse/send work before a payload transition. A restricted subject cannot create fresh work while the manifest is applied.

### 5. Governed redaction and derivatives

Raw receipt redaction must be a narrow function/trigger transition authorized by an actual locked privacy job/manifest item. A generic role check or caller-settable GUC is insufficient. Clear approved plaintext fields, record a content state and transition receipt, preserve IDs/original dedup hash/attestation/timestamps and justified financial facts. Existing replay of a purged receipt must resolve to the approved minimum proof without reinserting content or starting parsing. Active parse leases and external calls must finish safely or be fenced before transition; parser completion cannot recreate derivatives afterward. Raw reveal and investigation must return an explicit unavailable/redacted result with appropriate audit, not the original body.

Apply the same field plan to payer identity, private parsed columns/JSON, profiles, member identity, filenames, support/request text, results and audit metadata. Stable hashes are still personal data and require their own approved retention basis. Do not change the matching hash algorithm as an incidental cleanup.

For rosters, traverse all revisions, extraction/commit/result payloads, editor drafts, intents and recovery descendants. A subject in a multi-member JSON document needs precise field/row minimization; deleting all imports uploaded by that actor is neither complete nor appropriately scoped. Keep justified original provenance hashes, resource/SID/commit proof and expiry semantics while physically clearing eligible payload, including any retained original copy. A sidecar visibility flag leaves content present and does not count as erasure. Fence AI reprocessing and recovery transfers during this work.

For messages, revoke consent and stop new dispatch first. Cancel only safely unstarted queued jobs according to the current state machine. Existing outbox constraints/immutable triggers require a reviewed content transition or separation from retained proof. Keep minimal claim/session/body/destination hash, ledger snapshot and final/uncertain attempt bindings only under the policy. Do not clear a send-start fact, recycle an attempt ID, release a possibly used fence, or trigger resend. Financial journals, lines, balance snapshots, RWF totals and compensating reversal relationships remain byte/value invariant except explicitly approved identity separation; no balance recalculation is an erasure action.

### 6. Device, processor, copy and restoration proof

Add an explicit owner-bound native disposition API separate from ordinary disable/sign-out. Bind exact queue items to the request and policy decision, preserve unacknowledged required evidence, and acknowledge actual eligible ciphertext removal only after it succeeds. Account switching must never clear another owner's new data. Clear eligible protected snapshot files, browser bookmarks, in-memory views and stale Auth storage through their existing serialized/fenced paths. Native encryption keys are currently shared per store; deleting a shared key must not destroy another owner's required data. The internal gateway adds append-only encrypted request/attempt/callback/late evidence, ciphertext exports and original/view restore copies. Its compaction never frees identities for a new attempt, and its inactive restore carries no dispatch authority; include every copy without weakening those protections. Offline/unreachable devices remain an outstanding copy disposition; deletion from a screen is not device proof.

Inventory actual Storage owners/objects/versions and remote avatar/download assets before Auth deletion; source absence of upload calls is not proof of no hosted objects. Use supported object APIs with exact manifests and readback. Track processors, support systems, exports/downloads, replicas, logs/WAL, offsite and managed backups as separate child dispositions. Database UPDATE/DELETE proves logical application removal, not immediate destruction of old pages or physical copies.

Approved backup overwrite or demonstrable partitioned-key destruction must have an actual receipt, schedule and scope; do not erase a shared encryption key that protects retained records. Preserve minimal durable erasure tombstones outside restore rollback, and reapply them before a restored system enables user access, parsing, notifications or provider work. Processor `store:false` and an HTTP acknowledgement cannot substitute for actual configuration/retention evidence. No externally delivered SMS, downloaded export or provider-owned record is claimed erased without its own evidence and control basis.

### 7. Verification and communication

Receipt-only completion requires exact eligible field readback and preserved required evidence. Whole account completion additionally requires Auth/session removal or a documented scoped retained-access outcome, verified local/server dispositions, processor/copy outcomes, and a clear retained-basis statement. Record action codes, counts, hash/version bindings and exception references rather than plaintext. Expose a safe subject status receipt and capability-scoped operator status. Response obligations need an assigned operational owner, deadlines derived from the actual requirement, and measured escalation; no invented owner assignment is made here.

7. Outbox queued/claimed/send-start/uncertain/final states, lease takeover, session revocation and source-busy handling; no false no-send, released used fence or duplicate transmission.
8. Full before/after journal/line/snapshot/member reservation and balance checks; no altered RWF amount, consumed transaction identity, double entry or reversal relationship.
9. Holds created/released during execution, changed policy/source version, missing approval, worker killed between mutation and acknowledgement, bounded batch saturation and actual restart; receipts cannot be marked complete by a skipped/failed item.
