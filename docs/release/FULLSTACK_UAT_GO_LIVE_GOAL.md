# Fullstack UAT and Go-Live Goal

Prepared: 2026-05-24

## Goal

Execute and evidence a fullstack user acceptance test and production readiness decision for Collect, the Flutter and Supabase application in `/Volumes/PRO-G40/COOL`, with the explicit release objective of proving whether the current Flutter mobile app, isolated Flutter admin surface, Supabase database, Supabase Edge Functions, security controls, operational scripts, build artifacts, and human operator workflows are ready for public production launch. The work must treat UAT as an end-to-end business and technical gate, not as a narrow widget-test pass. It must cover the contributor app, collection creator flows, public directory flows, receiver/manual SMS flows, payment-intent and MOMO instruction flows, ledger/allocation behavior, role-scoped admin review, raw-SMS reveal, moderation, system health, audit logging, release builds, production configuration, linked Supabase readiness, platform security posture, and final go/no-go evidence.

The test effort must begin from the current repository facts, not from assumptions. The app is a Flutter project pinned to `/Volumes/PRO-G40/flutter_3_44`, currently reporting Flutter `3.44.0`, Dart `3.12.0`, and DevTools `2.57.0`. The package is `collect_app 0.1.0+1` and uses `flutter_riverpod`, `go_router`, `supabase_flutter`, `qr_flutter`, `intl`, `crypto`, `uuid`, and app-specific Collect models, repositories, security helpers, and widgets. The main app entrypoint is `lib/main.dart`; the admin entrypoint is `lib/main_admin.dart`. The main app routes include auth, home, collections, collection creation, collection detail, management, contribution, payment instructions, share, invite, ledger, public directory, receiver SMS, manual SMS, profile setup, settings, and a debug-only design system route. The admin app routes include login, denied, overview, collections, public requests, users, payments, payment events, unallocated payments, ledger, receivers, SMS metadata/details, audit logs, settings, feature flags, system health, and admin users. UAT must verify both route surfaces and preserve the stated product boundary: the main app does not rely on broad admin access, and real admin authorization is enforced server-side through Supabase RLS, security-definer RPCs, role/permission tables, and audit logs.

Before any human UAT session is accepted as valid, the preflight gates must be refreshed and recorded with exact command output paths. Required local gates are `/Volumes/PRO-G40/flutter_3_44/bin/flutter --version`, `make flutter-pub-get` if dependencies need refresh, `/Volumes/PRO-G40/flutter_3_44/bin/dart format --set-exit-if-changed .`, `/Volumes/PRO-G40/flutter_3_44/bin/flutter analyze --no-pub`, `/Volumes/PRO-G40/flutter_3_44/bin/flutter test --no-pub --concurrency=1`, `make release-secret-scan`, `make supabase-acceptance-matrix-json`, `make release-status-json`, `make supabase-go-live-gate-json`, and the existing Supabase readiness commands documented in `Makefile`. Current execution on 2026-05-24 found that format and analyzer are clean, release-doc tests pass, the full Flutter test suite passes with `87` tests, the redacted fallback secret scan passes, and the latest generated Supabase evidence bundle remains `NO-GO` with `7` pass and `5` blocked acceptance-matrix items because this runner cannot complete strict Postgres checks (`database_connectivity`). The earlier analyzer lint at `test/supabase_contract_test.dart:299` has been fixed. A Flutter `integration_test/` harness now exists for Android smoke coverage, but full human persona UAT remains pending.

The UAT execution must include persona-based business journeys and technical assertions. At minimum, run UAT for a contributor, collection creator, recurring group admin, public supporter, receiver or SMS operator, moderator, payments admin, compliance admin, non-admin user, and edge-case user. For each journey, capture setup data, user identity, route or surface used, steps performed, expected result, actual result, screenshots or logs where safe, database/RPC evidence, audit-log evidence, and pass/fail status. The contributor journey must prove sign-in, approved public collection discovery, payment-intent creation, MOMO/USSD instruction visibility, sanitized reference confirmation, and no accidental payment API or raw receiver data leak. The creator journey must prove private collection creation, receiver MOMO capture, public-listing request, QR/link share, and default privacy. The public supporter journey must prove approved-only public directory visibility and contribution-step-only receiver details. The receiver/manual SMS journey must prove consent-gated SMS handling, sanitized manual SMS ingestion, parse behavior, conservative fallback on ambiguous data, and no persistence of raw parsed phone fields in public views. The moderator and payments admin journeys must prove public-request review, unallocated event review, manual allocation with reason, idempotency, ledger single-posting, and denial for users without lane permissions. The compliance journey must prove raw SMS is masked by default, reveal requires permission and reason, and reveal is audited. The non-admin journey must prove both client-side and server-side denial. Edge cases must include duplicate SMS/transaction references, invalid amount, non-Rwanda phone number, expired intent, ambiguous amount, missing receiver authorization, failed Edge Function auth, and retry-safe behavior.

The backend UAT must be fullstack and linked to Supabase evidence. It must validate that the remote public schema matches the repo-owned contract, that every public base table has RLS enabled, that public functions have explicit `search_path` posture, that advisor warnings remain bounded and performance warnings remain clean, that Edge Functions have the intended auth mode and deployment inventory, and that no service-role, OpenAI, WhatsApp, SMS hook, or Supabase secret is present in Flutter-visible configuration. The latest generated evidence bundle reports pass evidence for schema object count `160/160`, RLS `28/28`, function search path `57/57`, local Edge Function auth contract UAT, redacted secret scan, operational report, and operator handoff generation. It reports blocked status for code-owned readiness refresh, remote Edge Function endpoint/secret-name readiness refresh, platform readiness, exceptions, and final go-live because this runner cannot complete strict Postgres checks (`database_connectivity`). Earlier evidence still shows unresolved operator platform blockers: `auth_hibp_leaked_password_protection`, `auth_captcha_bot_protection`, `supabase_organization_plan`, and `supabase_pitr`. UAT must therefore distinguish current verification connectivity from actual code-owned drift. No public production launch may be approved while CAPTCHA/bot protection and HIBP leaked-password protection remain disabled, because those are currently treated as non-exceptionable blockers in the repo gate. Free-plan project-pause risk and PITR/RPO risk may only proceed if resolved or covered by a valid signed release-owner exception after the non-exceptionable blockers are resolved.

Production readiness must follow current official guidance, not stale assumptions. Flutter integration testing guidance says the `integration_test` package is the SDK-supported path for full-app tests and can run on real Android and iOS devices; this repository now has an Android smoke harness, but persona-level mobile and iOS UAT still need signed release evidence. Flutter Android release guidance requires release signing, manifest review, unique application ID, correct Internet permission for production network calls, Gradle configuration review, and awareness that release APK/AAB builds use code shrinking. Flutter iOS release guidance requires proper version/build numbers, `flutter build ipa`, archive validation, and App Store Connect/TestFlight distribution readiness if iOS is in release scope. Supabase production guidance requires Security Advisor and Performance Advisor review, RLS on exposed tables, SSL enforcement, network restrictions, MFA for administrative accounts, custom SMTP/deliverability planning, load testing on staging where possible, PITR or accepted RPO, and paid-plan posture if project pausing is unacceptable. Supabase Edge Function auth guidance requires user JWTs for signed-in calls, publishable or secret keys in the correct headers for service or public-client calls, and `auth: none` or `verify_jwt = false` only for genuinely public or externally signed webhook endpoints with separate verification. Supabase changelog research also found recent breaking-change and platform-change items relevant to release review, including tables not being exposed to Data and GraphQL APIs automatically, Postgres 14 support ending on July 1, 2026, self-hosted PG 15 to 17 changes, and automatic PostgREST retry behavior in official clients; the UAT must confirm this app's exposed API assumptions, remote Postgres version, and retry/idempotency posture.

The final deliverable must be a go-live packet that a release owner can sign without guessing. It must contain a dated UAT execution report, an updated production readiness checklist, a go/no-go decision, release blockers, sanitized evidence bundle location, build artifact paths, command transcript summaries, exact device/browser matrix, test data ledger, unresolved risk register, signed exception file if any exceptionable platform risk remains, and a rollback/incident plan. Evidence must not expose raw SMS, phone/MOMO numbers, tokens, production secrets, service-role keys, provider secrets, or unrestricted customer data. If any source, dependency, platform config, Supabase migration, Edge Function, or operator setting changes during UAT, the relevant gates must be rerun after the change. The launch decision is GO only if local Flutter hygiene is green, device/persona UAT is complete and signed, production Android and any scoped iOS/admin web builds are verified, Supabase code-owned readiness remains green, Supabase platform blockers are resolved or validly exceptioned where allowed, the final `make supabase-go-live-gate-json` approves release, and the worktree/release branch is intentionally reviewed so unreviewed broad drift is not shipped by accident. Otherwise the decision remains NO-GO with exact blockers and next actions.
