# Admin notification page before delivery counts — 29 September 2026

**Status: local candidate; production NO-GO.** The additive [migration](../../../supabase/migrations/20260929110000_admin_notification_page_before_delivery_counts.sql) is the 134th numbered migration in the current source tree. A separate PostgreSQL 17.6 Supabase fixture passed a clean 134/134 application replay. It has not been applied to an authorized hosted project; the preceding 133-migration restored financial fixture remains unchanged.

The existing `public.admin_list_notifications` function materialized a filtered CTE that included two correlated delivery counts, then reused that CTE for both the page and exact total. On 10,000 synthetic events plus one existing event, nested `EXPLAIN ANALYZE BUFFERS` showed **10,001 index probes for each delivery count** to return a 25-row first or deep page. The candidate first selects the requested page, computes both delivery counts in one lateral aggregate for those 25 events, and separately computes the exact filtered total. It adds created-time and status/created-time indexes for Admin page access. The result keys, row formatter, search, status filter, sort behavior, limit/offset clamps and permission assertion remain the same.

The [parity runner](../../../scripts/tests/admin_notification_page_parity_uat.py) compared complete old and candidate JSON documents in one rollback transaction for **ten cases**: first descending and ascending pages, failed ascending, deep descending, type and Collect ID searches, no match, unknown sort, clamped limit/offset and expired offset. The [sanitized transcript](parity.stdout) passed all ten. The test also checked that `anon` cannot execute the function, `authenticated` can, and both proposed indexes exist. No seeded row persisted.

## Historical 133-to-134 upgrade

The task-owned 133-migration financial fixture still matches its recorded 16-row historical financial/evidence snapshot. A custom archive of that fixture, SHA-256 `6037999ae339ecadf2494100e24e27da1c2d24b1087e7e550762e50edec446b9`, was restored into a new empty `template0` database in the separate notification QA project. The first attempted same-cluster restore rolled back because `pg_cron` permits creation only in its configured database; its empty task clone was removed after an emptiness check. In the separate project, cron jobs were disabled, `pg_net` was directed to `template1` with batch size zero, and the restore succeeded. Before migration 134, the source and restored database matched across 129 COPY sections, 1,327 rows, four sequence statements and a normalized schema/ACL dump with SHA-256 `2826135177bfe7fdbb9ebcebd17e1eb1ef6c745ffb8b8295324775341f6c219d`.

Migration 134 and its migration-history row then committed in one guarded transaction. The [read-only verifier](../../../scripts/tests/verify_historical_notification_upgrade.py) found the same 16-row financial/evidence SHA-256 `c294b544c37c730475fda5d76c6b8c5471a3c12535ff345fd7e3dc914281a9d4`, posted/review statuses, receipt contract version and RWF 1,500 group balance. The other 128 table-data sections, their 1,194 rows, and sequence statements still matched the 133-migration source; only the migration-history row increased from 133 to 134. Anonymous notification execution remained denied, authenticated execution was granted, and the two page indexes existed. One scheduler metadata row was preserved, while job launch remained disabled. The [rollback-only Admin check](historical-134-uat.stdout) passed first, expired-offset and filtered pages after a database restart; its temporary approval/session did not persist. The [sanitized upgrade report](historical-134-upgrade.json) records the fixed fixture provenance, hashes and readbacks. The source financial fixture remains at migration 133. Rerunning this verifier requires the task-owned local fixtures and ignored source archive; it is not a portable CI or clean-checkout test.

The [plan benchmark](../../../scripts/tests/admin_notification_paging_benchmark.sql) ran the authenticated Admin RPC at 1,000 and 10,000 synthetic events; the [verifier](../../../scripts/tests/summarize_admin_notification_paging_benchmark.py) checked case totals, rollback markers and nested actual-buffer plans. At 10,000 events, first-page delivery probes fell from **10,001 twice** to **25 once**; shared-buffer hits in the Admin query fell from **60,221** to **330**. Single local first-page timings were **38.115 ms** and **3.851 ms**; failed-status timings were **14.910 ms** and **2.529 ms**; deep-page timings were **37.612 ms** and **5.525 ms**. These are one-run observations, not p95/p99 or a production capacity claim. The [summary](summary.json) includes raw private-log hashes and both 1,000- and 10,000-row plans. The raw logs remain in ignored task-owned `.cache` storage.

The independent restore verifier matched all 1,327 original rows, global roles, schema/ACL and the 16-row financial snapshot after the rollback-only runs. On 29 September, the separate [clean replay report](clean-134-replay.json) recorded 134 passing source-hash-matched migrations from an empty Collect application/Auth fixture, a synthetic bootstrap owner, PostgreSQL 17.6, and cron jobs disabled. Database readback found 134 migration rows, the expected final version, both new indexes, authenticated execution and anonymous execution denial for the notification RPC. This clean replay does not include historical customer data or an authorized deployment.

The candidate still computes an exact total over all filtered events and a deep offset page must walk skipped index entries. Search by substring is not accelerated by the new B-tree indexes.
