# COOL / Collect
# Production-readiness audit

**Assessment date: 27 September 2026**  
**Decision: NO-GO for a new production rollout until the mandatory gates below are closed.**  
**Deliverables: critical report, 32-finding register, 92-task backlog, source register and sanitized validation evidence.**

This is a source-and-evidence audit of the specified COOL Google Drive workspace, not a penetration test, regulatory opinion, production certification or declaration that an existing service is down. It distinguishes the original source tree, separately delivered candidate overlays and the actual hosted system. New audit files are to be filed in the owner's COOL folder without overwriting original code, historical deliveries or access permissions.

## Executive decision

Collect has a meaningful implementation, not an empty concept. It has a shared Flutter member application, an isolated Flutter-web admin entrypoint, a static public site, Supabase-backed identity and financial records, deterministic receipt extraction, native Android encrypted receipt capture and a substantial test/release-tooling investment. Existing code includes useful ownership, concurrency, lease, audit and permission boundaries. A September 10 repair report records 765 Flutter tests and 54 Deno tests against an earlier checkout. Those historic results deserve credit, but they do not validate the later candidate branches. [S02] [S03] [S11] [S14] [S18] [S22] [S25]

The current risk is the gap between implemented fragments and one reproducible, validated release. Original instructions still require the design rule the owner explicitly retired. Two Increment 11 packages each contain 112 source files but are not interchangeable. The production backend was not accessible through the connected Supabase tool, and no current signed-build, device, migration, provider or store-approval evidence was established. Consequently, neither the quantity of uploaded files nor the number of passing tooling assertions establishes production readiness. [S01] [S04] [S05] [S25] [S26]

The most urgent confirmed finding is outside the application code: the COOL root and an inspected review-environment file have anyone-with-link writer permissions. The review file contains a review identity/OTP and signing-related identifiers/path. No private-key bytes were found in that file, no credential was used, and its current validity is unknown. Restricting the source/evidence trust boundary and assessing any active review credentials must precede a release. This is an exposure finding, not proof that unauthorized access occurred. [S33] [S34]

The next priorities are to reconcile and compile the candidates, make the attestation contract fail closed, prove receipt-to-ledger correctness under faults, prevent silent native evidence loss, and validate real operator-device behavior. History response paging needs query-plan work because it first materializes and hashes the full matching history. Documentation must be aligned to the latest Rwanda-only scope rather than the old bank/diaspora and OpenAI-only flows. [S06] [S07] [S11] [S12] [S15] [S16] [S18] [S20]

**Recommended strategy:** retain the present Flutter/Supabase architecture for the first controlled release. Establish one protected canonical repository and release manifest; finish integration and security work before adding new features or undertaking a broad native rewrite. Use a production-like isolated environment, then physical MTN/Airtel UAT, independently reconciled pilot activity and accountable signoff. A narrower pilot can be justified only after its own mandatory controls pass; “pilot” must not be used to waive financial integrity, privacy or distribution requirements.

## 1. Method, evidence and limitations

### 1.1 What was examined

The audit traversed the root, deployment, native receipt, Supabase function/migration, release-document and CI areas; read selected high-risk source files and operating documents; inspected sharing metadata; parsed the supplied Git index; compared original file bytes with indexed blobs; and compared both Increment 11 candidate source trees. It also read current primary platform and regulatory sources listed in the source register. The tools used included Google Drive/Files, Supabase discovery, the relevant product-design, Android QA and Supabase skills, local Ruby/Node/Python tooling, and public primary-source research. Chantal authority discovery was attempted but could not connect, so it supplied no legal conclusion.

The valid Git index contains 1,569 entries, including 185 under lib, 168 under supabase, 256 under scripts, 357 under docs and 97 under test. These are indexed-path counts, not counts of every currently accessible Drive object, tested modules or reviewed lines. A complete recursive audit of every file, Git object and deployed endpoint was not performed. [S35]

### 1.2 Three states that must not be conflated

| Layer | Evidence available | What it does not prove |
|---|---|---|
| Original Drive source | Actual source and configuration reads, metadata and selected byte checks | That the snapshot is the canonical remote commit or currently deployed |
| Delivered candidate overlays | Exact archive/source hashes, documented deltas, tests and installers | Integration into the complete app, successful compilation or release approval |
| Hosted production | Historic documents and intended configuration only; current project discovery returned no accessible projects | Current schema, grants, CAPTCHA, PITR, provider configuration, availability or distribution status |

A local config.toml is not a hosted-settings export. An authored test is not an executed test. A successful fixture installer is not a successful application build. A checksum in an editable folder is not independent approval. Findings below label confirmed observations, conditional risks and verification gaps separately.

Flutter and Dart executables, a device/emulator and an accessible linked Supabase project were unavailable. There was no app compilation, whole-app test run, real-device interaction, visual acceptance, live RLS/ledger evaluation, active security attack, real payment, provider SMS, deployment, restore or permission mutation. Public-site fetch attempts failed from the inspection environment and do not establish an outage. Current GitHub billing/CI status, store decisions and hosted protections were not verified. Full implementation claims must wait for these evidence gaps to close.

## 2. Current architecture and product boundary

| Surface or layer | Observed implementation | Production implication |
|---|---|---|
| Member app | Flutter, Riverpod and routed feature modules | Shared UI is reasonable; financial state and native handoff need actual integration tests |
| Android receipt boundary | Protected-receipt design, owner-bound AES-GCM queue, asynchronous local processing | Privacy controls are promising; durability, overflow and recovery need proof |
| Admin surface | Separate Flutter-web entrypoint, permission-scoped operations | Navigation scope is not authorization; server reason/role checks need actor tests |
| Public website | Static build and separate deployment workflow | Appropriate separation for marketing/SEO; source copy and screenshot provenance drift remain |
| Backend | Supabase Postgres, RPCs, Edge Functions and intended Realtime/Storage use | The database is the financial authority; actual deployed version/grants are unknown |
| Receipt extraction | Deterministic Rwanda MoMo parser in the inspected active path | Fixed confidence is a parser heuristic; OpenAI-only operating instructions are stale |
| External services | WhatsApp OTP delivery, Play Integrity, Firebase push and static hosting | Their production identifiers, quotas, approvals, ownership and failures must be validated |

Source basis: [S02] [S03] [S10] [S11] [S12] [S13] [S14] [S15] [S18] [S20] [S21] [S22] [S36].

The intended financial flow should be documented as: authenticated member and eligible group → exact payment intent → external MoMo USSD authorization → consented recipient SMS capture → durable authorized ingestion → deterministic extraction → uniquely authorized allocation → atomic confirmed posting → notification/readback. Opening USSD, receiving a broadcast, parsing a number and sending a notification are distinct events. Only the approved database transition may establish a confirmed ledger state. The implementation must prove that distinction under retries, collision and recovery—not merely on a successful demonstration.

The latest migration disables retired bank features and restricts new activity to Rwanda/RWF while retaining historical records. Its NOT VALID constraints should not be automatically removed: historical exceptions may be intentional, and current-write enforcement and migration compatibility need testing. Documentation that still expects diaspora SEPA/Revolut activity is not an authoritative description of this candidate. Likewise, this audit does not characterize the repository as a licensed deposit-taking or lending system merely because it displays group contribution balances. [S15]

## 3. Prioritized findings

P0 means a mandatory containment or release-blocking condition for the proposed rollout. It does not mean that every P0 is a proven exploit. P1 is required hardening or acceptance work before broad rollout; P2 is a strategic improvement after correctness and release controls. Owners in the task register are recommended accountable roles, not statements that a named person has accepted an assignment.

### F01 · P0 · Link-writable source and audit evidence

**Evidence status:** Confirmed metadata. **Area:** Security.

COOL and the inspected review environment file both return anyone/writer permissions. Link discovery is disabled, not link access.

**Why it matters.** Anyone obtaining the link can affect source integrity; evidence files and hashes in the same editable boundary do not independently establish authenticity.

**Required response.** Restrict access to named accounts, preserve a trusted snapshot, review change/access evidence, and segregate sensitive source and immutable release evidence. No permissions were changed during this audit. [S33] [S34] [R03]

### F02 · P0 · Review credentials in the shared workspace

**Evidence status:** Confirmed file inspection; validity unknown. **Area:** Security.

The review environment file contains a nonempty review identity and OTP, signing account identifiers and a local key-file path. No secret values are reproduced.

**Why it matters.** An active review credential could expose the review account; identifiers and a path are not proof that private signing key bytes leaked.

**Required response.** Test validity through the authorized account owner, revoke active review access, inspect related sessions and distribution, remove sensitive material from shared delivery copies, and inventory ignored files and archives as well as Git. [S34] [S35] [R03]

### F03 · P0 · Two conflicting Increment 11 candidates, no canonical integrated release

**Evidence status:** Confirmed byte comparison. **Area:** Release integration.

Both branches have 112 source paths; 108 overlap, 104 match, four shared paths differ and each branch has four exclusive paths. Original AGENTS remains unrevised.

**Why it matters.** Applying packages by date or folder name can lose fixes; a checksum proves transport integrity, not correctness or integration.

**Required response.** Choose a protected canonical checkout, review the four shared conflicts and eight exclusive files, retain both useful test sets, create one reviewed commit and rebuild every target from it. [S01] [S04] [S05] [S35]

### F04 · P0 · Latest Dart changes are not application-validated

**Evidence status:** Candidate evidence gap. **Area:** Release integration.

Increment receipts explicitly distinguish authored Dart tests from executed tooling tests. SDK-equipped integrated execution for the latest merged candidate was not available.

**Why it matters.** Compilation errors, API mismatches and runtime regressions can survive string checks and fixture installers.

**Required response.** Run pinned formatting, full analysis and all unit/widget tests; build signed production Android, iOS and both web surfaces; preserve command outputs, commit and artifact identity. [S03] [S04] [S05] [S22] [R18]

### F05 · P1 · Git snapshot does not establish a reproducible working checkout

**Evidence status:** Confirmed index comparison; object completeness unknown. **Area:** Release integration.

The Git index contains 1,569 entries. Six of seven compared original files match indexed blobs; the Rwanda-only migration is not present in the index. The inspected pack folder did not expose a matching .pack file.

**Why it matters.** The Drive snapshot may contain uncommitted work or incomplete object transport. Neither possibility is a proven malicious change.

**Required response.** Reconstruct from the authorized source remote, run status/fsck, compare worktree and migration hashes, identify intended changes, and capture exact commit plus reproducible build inputs. [S15] [S35]

### F06 · P1 · Retired design rule remains an active instruction

**Evidence status:** Confirmed source. **Area:** Governance.

Original AGENTS and CI still refer to the retired rule, despite owner instructions and revised candidate policy.

**Why it matters.** Conflicting instructions can regenerate prohibited checks and block otherwise valid work.

**Required response.** Remove active references from the integrated source, scripts and CI; keep historical archives clearly non-authoritative. The revolut-design skill is the sole design authority. [S01] [S22] [S04] [S05]

### F07 · P0 · Rwanda-only runtime conflicts with dual-rail and AI-only documentation

**Evidence status:** Confirmed source conflict. **Area:** Governance.

README and the 25 September migration are Rwanda-only; architecture, operations and parser documents still mandate bank/diaspora behavior or OpenAI-only SMS parsing.

**Why it matters.** Operators can deploy retired functions, users can receive inaccurate disclosures, and tests may assert the wrong product contract.

**Required response.** Approve one current product matrix and regenerate architecture, public copy, privacy notices, deployment allowlists, operations and test expectations from that agreed scope. [S02] [S06] [S07] [S15] [S29] [S30]

### F08 · P0 · Attestation contract downgrade is accepted by Edge code

**Evidence status:** Confirmed source; deployed exploitability unverified. **Area:** Backend security.

Missing contract RPC or a value other than one selects legacy SMS ingestion; finalization also returns legacy_contract when the expected version is absent.

**Why it matters.** A partially deployed or drifted environment can silently weaken the required receipt-security boundary.

**Required response.** Require a supported contract version in production; return unavailable on unknown/missing versions and prove by integration tests that legacy paths cannot post without required authorization and evidence. [S11] [S12] [S14] [R08]

### F09 · P0 · Auth hook has an alternate static-secret authorization path

**Evidence status:** Confirmed source; configuration-dependent exposure. **Area:** Authentication.

The handler supports both signed-hook verification and an alternate shared-secret path. A production dry-run option can acknowledge without delivery.

**Why it matters.** A leaked alternate secret or accidental dry-run setting can invalidate assumptions about replay resistance and successful OTP delivery.

**Required response.** Use the intended signed webhook route in production; reject stale/replayed/mutated requests, disable dry-run in release configuration and contract-test successful versus failed delivery acknowledgements. [S10] [R06] [R07]

### F10 · P1 · OTP abuse and provider failure controls need completion

**Evidence status:** Source-observed control gap. **Area:** Authentication.

The database serializes five requests per phone per ten minutes. It stores IP hashes but this function does not impose an IP/global budget. Provider calls have no explicit timeout in the inspected handler, and error-body logging is bounded but not field-allowlisted.

**Why it matters.** Distributed phone rotation, provider latency and diagnostic payloads can increase cost, latency or sensitive-data exposure.

**Required response.** Add trusted-edge IP/account/global budgets, delivery timeouts and safe structured logging; validate CAPTCHA where appropriate in the custom flow, not merely as a dashboard toggle. [S10] [S17] [R06]

### F11 · P0 · Device integrity and parser completeness are not settlement proof

**Evidence status:** Confirmed parser behavior; financial boundary verification required. **Area:** Financial integrity.

A synthetic arbitrary-sender message with an MTN body hint and a masked payer receives network=mtn_momo and confidence=0.96 without a transaction ID. This does not demonstrate a database posting bypass.

**Why it matters.** Treating a heuristic parser score or recognized device as verified funds risks false ledger confirmation.

**Required response.** Document independent evidence requirements, retain deterministic extraction, enforce unique receiver/payer/amount/time/intent matching, quarantine ambiguity and prove no unauthorized or duplicate posting through transactional tests. [S11] [S12] [S13] [S14] [S15] [R04]

### F12 · P0 · Exactly-once financial outcomes lack current end-to-end proof

**Evidence status:** Current validation gap; positive source controls exist. **Area:** Financial integrity.

Parsing has lease and replay handling, while the architecture assigns allocation and ledger posting to database functions. This audit did not execute the full allocator, reversal or current permission matrix.

**Why it matters.** Retries, crash windows, collisions and partial deployment may leave duplicate credits, stuck evidence or misleading balances if the complete transaction contract is not proven.

**Required response.** Exercise crashes before/after durable ingest, parser insert, allocation, finality and notification; reconcile group/member balances to immutable postings and distinguish receipts, allocated events and confirmed records. [S11] [S12] [S15] [S09]

### F13 · P0 · Queue capacity and corruption can lose unprocessed receipt evidence

**Evidence status:** Confirmed source behavior. **Area:** Mobile reliability.

The native queue is capped at 100. A decryption/read exception deletes encrypted and legacy queues and returns an empty array; failed writes and full queues are logged.

**Why it matters.** A genuine receipt may never reach the server and may be unrecoverable because inbox backfill is deliberately absent.

**Required response.** Persist a non-sensitive loss/corruption indicator; design controlled recovery and capacity management, measure overflow on realistic bursts and never convert evidence loss into payment success. Preserve explicit consent-revocation deletion. [S18] [S19] [S29] [R17]

### F14 · P1 · Process-local worker is not durable background delivery

**Evidence status:** Confirmed source; observed device behavior untested. **Area:** Mobile reliability.

SmsQueueWorker is a single daemon executor. The receiver raises a queue event; this alone is not a persistent OS upload job.

**Why it matters.** App termination, reboot, Doze and vendor restrictions can delay or strand receipt ingestion.

**Required response.** Define foreground and background guarantees; use a suitable persistent scheduler where supported, constrain it by current owner/consent, and test lifecycle recovery on real MTN/Airtel devices. [S19] [S20] [R05]

### F15 · P1 · Native and server capture limits and filters differ

**Evidence status:** Confirmed source. **Area:** Mobile reliability.

Native capture uses 2,000 characters and a sender/body-hint filter; server ingestion bounds raw text by bytes, with a 4,096-byte body limit.

**Why it matters.** Unicode, multipart and altered provider templates can be rejected at different layers; broad body hints are classification, not source authentication.

**Required response.** Publish one versioned capture contract and bilingual provider corpus; test UTF-8 limits, mixed multipart senders, duplicate broadcasts, delayed messages and provider-template changes. [S11] [S13] [S19]

### F16 · P1 · Response pagination still performs whole-history work

**Evidence status:** Confirmed SQL; scale unmeasured. **Area:** Database performance.

history_page materializes payment_history JSON, ranks and hashes the matching dataset, and computes aggregates before limiting rows. Recent-intents selection first creates the full intent list.

**Why it matters.** Per-page database work can grow with total history and may cause repeated refreshes as revisions change during active use.

**Required response.** Benchmark query plans on representative isolated datasets; move to indexed relational keyset retrieval and versioned aggregate snapshots where justified, preserving authorization and correctness. [S15] [S16]

### F17 · P1 · Other collection and notification reads need bounded contracts

**Evidence status:** Source-observed and broader inventory gap. **Area:** Backend data.

The current collection RPC aggregates all visible collections; not every remaining list or notification query was traced to a bounded server contract.

**Why it matters.** Client-only pagination or hidden caps can truncate lists and produce misleading totals.

**Required response.** Inventory each list RPC/query and require stable ordering, filters, explicit total/continuation semantics and scale tests; treat absent aggregates as unavailable rather than fabricated zero. [S15] [S04] [S05]

## 5. Research-backed architecture and operational recommendations

### 5.1 Keep the architecture; improve its trust and release boundaries

A shared Flutter codebase plus a narrowly native Android receipt boundary is coherent for this product. A full rewrite would not solve uncertain database deployment, writable artifacts, financial evidence ambiguity or absent store approvals. Prefer a measured performance program and targeted native reliability improvements. Flutter's own performance guidance supports lazy construction and reducing expensive rendering work, but none of those optimizations guarantees a frame rate on untested devices. [R09]

Separate the runtime repository from preservation archives. Historical revisions must remain recoverable, but they should not sit inside the active deployment context or appear as additional “latest” policies. Use one signed-off commit, append-only release records, protected environments and a narrow deployment allowlist. The original Makefile still defines the evidence-consistency target invoked by CI; the finding is a source/document-baseline contradiction, not proof that the target is missing.

### 5.2 Security must fail closed at version boundaries

Treat the database attestation contract as a production prerequisite. An unavailable contract is not permission to use an older path. During migration, a deliberate, expiring compatibility window needs an approved policy, version telemetry and proof that it cannot bypass financial safeguards. Client-side ownership checks and RLS are complementary, not substitutes; security-definer routines require explicit authorization and execution-grant review. [S11] [S12] [S15] [R08]

The existing SHA-pinned Actions and read-only default GitHub token are good foundations. Apply the same discipline to production credentials: do not permit repository-variable configuration to make arbitrary PR-controlled code a production verification job. Give a dedicated trusted environment the least authority required, and keep synthetic tests independent of live secrets. [S22] [S23] [R03]

### 5.3 Separate extraction accuracy, receipt authenticity and financial finality

Use deterministic parsing where the format is stable, with a versioned real-world corpus and explicit rejection of unsupported templates. AI can assist an exception analyst or extract non-authoritative fields only under appropriate data controls; it must not fill missing sender identity, fabricate a transaction reference or infer that funds settled. In the inspected source, complete-format confidence is a constant, not a calibrated probability. Retain raw evidence under restricted access for approved investigation, but minimize its lifetime and disclosure.

Play Integrity can support device/application risk assessment and request binding. It does not independently verify the operator's settlement records. The financial boundary must also address duplicate broadcasts, body modifications, masked-payer collisions, reversal, delayed receipt arrival, concurrent pending intents and the crash between durable ingestion and acknowledgment. [S13] [S14] [R04]

### 5.4 Design reliability for real receiving phones

An executor moves work away from the UI thread; it does not establish a persistent upload lifecycle. A suitable scheduler must respect the current account, consent, retry policy and operating-system constraints. Preserve encrypted queue data until durable authorized ingestion is confirmed, and distinguish intentional consent-revocation deletion from loss caused by corruption or unavailable keys. The latter needs persistent safe status and an operational recovery route. [S18] [S19] [S20] [R05]

The Google Play financial/money-management exceptions are subject to review and approval; declaring receipt capture as a core feature is necessary but not sufficient. Verify the current release-specific approval rather than interpreting absence of READ_SMS as unrestricted use. A PWA or differently distributed binary should not be presented as automatically equivalent to the approved Android receipt workflow. [R01]

### 5.5 Recovery is broader than PITR

The earlier instruction to “enable PITR” is incomplete and its current status is unknown. Choose and fund an RPO/RTO; inspect actual restore points; back up object bytes as well as database metadata; and restore into a separate controlled environment. Supabase explicitly distinguishes database backups from Storage objects. Validate authentication state, revoked capabilities, queues, policy grants, service configuration and reconciliation before reopening writes. Preserve independent backups and evidence outside the same writable account boundary. [S09] [R02]

### 5.6 Privacy and legal classification follow actual activity

Rwanda's official DPO guidance addresses registration and authorization for storing personal data outside Rwanda. Verify those records for the actual provider geography and processing map; do not infer compliance or noncompliance from source alone. De-identified identifiers can still be personal data, and group affiliation can reveal sensitive context. Review retention, breach handling, access and processor arrangements with qualified counsel. [R12] [R13]

Separately, counsel should assess the actual control of funds, initiation and aggregation against current Rwanda payment law and implementing rules. The legal plugin connection did not succeed, and a current applicable BNR licensing determination was not obtained; this report is not an exemption opinion. Product language should accurately describe what Collect does and must not imply bank, deposit or credit authority it has not established. [R14]

Account deletion should be an implemented user journey, not only a policy paragraph. Apple requires in-app initiation for covered account-creating apps, with appropriate treatment of legally retained data. The actual retention grounds, requests, timing and accounting-evidence boundaries must be documented and tested. [R15]

## 6. Release-gate model

| Gate | Exit requirement | Decision owner |
|---|---|---|
| G0 — Containment and trusted access | Restricted source/evidence access; review credentials assessed; exposed active credentials revoked; production secrets isolated from untrusted workflows | Workspace owner and security lead |
| G1 — Canonical integration | One scope, repository, commit and dependency set; branches reconciled; active retired-rule references removed; source status clean | Engineering lead and release owner |
| G2 — Application and backend correctness | Actual formatter/analyzer/tests, isolated integrated platform, strict security contracts, actor matrix and financial invariants pass | QA, backend security and finance controls |
| G3 — Operability and recovery | Current hosted readbacks, required checks not skipped, backups/restore and RPO/RTO verified, alerts and quotas operating | Platform/SRE and business owner |
| G4 — Device, UX, distribution and legal acceptance | Signed builds, real MTN/Airtel lifecycle UAT, web upgrade tests, accessibility, accurate store/provider/privacy/regulatory evidence | Product, compliance and release owner |
| G5 — Controlled release | Immutable release manifest, independently reconciled limited pilot, rollback/stop-write ability and accountable decision | Release board / accountable product owner |

Dependencies overlap; these are evidence gates rather than calendar promises. A missing prerequisite must be reported as BLOCKED, not skipped-success. Any accepted residual risk must name an owner, affected population, compensating control and expiry. No evidence from an older commit should silently satisfy a changed high-risk flow.

### Suggested pilot acceptance targets — proposals for owner approval

Financial correctness should tolerate no observed unauthorized posting, duplicate economic-event credit or unexplained reconciliation difference in the acceptance corpus and pilot. Each consented receipt should have an observable terminal outcome or a visible actionable exception, not disappear into an empty queue. A breached or expired authorization must fail closed. These are proposed release acceptance invariants, not a claim that the current system meets them.

Latency, availability, maximum queue age, restore times and exception staffing require measured baselines and explicit business choices. Start by recording capture-to-durable-ingest, ingest-to-parse, parse-to-confirm/exception and confirm-to-notification separately. Provider delivery time, device connectivity and server processing should not be blended into one misleading SLA. Fix targets from expected transaction volume, device quality and support capacity rather than inventing a performance score in this audit.
