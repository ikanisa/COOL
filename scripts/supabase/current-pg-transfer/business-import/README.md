# Synthetic collection/principal transfer candidate

This directory contains an executable **synthetic-only experiment**, not a Supabase migration, deployment, import command, or authorization to transfer current data. `mode: 'managed'` fails before a connection is created. Before a transaction, the importer checks for a Unix-socket connection, cluster and database names both equal to `collect_business_import_fixture`, and the non-superuser `fixture_operator`. These checks neither enforce PostgreSQL 17 nor prove that a server is disposable; names, socket, and role can be imitated. Callers must use only the owned synthetic harness, which creates a disposable PostgreSQL 17 instance. No live mapping, key, principal, collection, fence, or database was created, read, or modified here.

## Bounded behavior

Within the fixture, the candidate inserts exactly one `src.collections` row into `app.collections`. Its schema mirrors the collection columns and principal foreign key in `20261020134444_collect_curated_platform_baseline.sql`. It preserves every column and historical timestamp byte-for-byte as represented by PostgreSQL except `creator_user_id`, which is changed from the explicitly pinned source user to the explicitly pinned cloud user. The source creator is retained in the transactional receipt; the cloud user's existing Auth-to-app-user link and both app users are neither created, changed, merged, nor deleted. Identity is never inferred from email.

Before insert, the plan binds an operation ID, both user IDs, both Auth IDs, the source collection ID, both fence epochs, exact snapshots of both users, Auth rows, and principal links, the complete source collection, a fixture evidence row, and the expected target postimage. Snapshots are PostgreSQL `jsonb` textual representations bound with a domain-separated HMAC; a separate caller-supplied digest pins the plan. The fixture key is generated during the test and never stored in a receipt. Before the first await, both entry points copy and freeze the flat primitive plan, pin the digest and connection function, and copy the key into an internal buffer that is cleared on completion. They reject accessor-backed or proxy plans and options, nonprimitive plan fields, and shared-memory key buffers. The target ID, slug and non-null share-code hash must be absent. `SHARE` relation locks hold fixture source, identity, evidence, fence and admission state, while target collection and receipt relation locks serialize imports. Enabled fixture immutability and insert-fence triggers and unsettled or uncertain admissions are checked. This is an in-one-transaction, **single PostgreSQL database** demonstration; it is not a cross-database fence or a distributed transaction.

The evidence row requires a reviewed fixture object-graph claim, no unresolved references, matching fixture key/AAD digests, and an explicit fixture claim that changing the creator does not change AAD. Even when those booleans are present, any row in the fixture dependency table refuses the transfer. The fixture includes an invented ciphertext value and tests its exact preservation. These test attestations do not establish any real key, ciphertext provenance, AAD rules, graph completeness, dependent-history ordering, or source/cloud identity mapping. The experiment cannot transfer a collection with fixture dependent history, nor does it migrate financial rows, attachments, Storage objects, or historical records.

The receipt is inserted atomically with the collection and retains original source attribution, plan/snapshot digests, the cloud principal, and the expected output digest. Same-plan replay checks the receipt and full postimage without inserting again. If `COMMIT` acknowledgement is lost, the writer reports `commit_unconfirmed_do_not_retry`. A separate **read-only**, repeatable-read reconciliation compares the pinned plan, current target identity, receipt and exact postimage; an absent receipt reports `receipt_not_visible_do_not_retry` because the original transaction may still be in flight. It never automatically retries. The fixture receipt table and privileges are illustrative, not a tamper-resistant managed audit design.

## Testing

From the repository root:

```sh
node --test scripts/supabase/current-pg-transfer/business-import/import.test.mjs
```

The tests start a temporary, private, owned PostgreSQL 17 instance using `../test-support/owned-pg17.mjs`; `COLLECT_SYNTHETIC_PG_BIN` can select a local PostgreSQL 17 bin directory. The fixture is stopped and removed after the test. Assertions cover managed-mode refusal before connection; mutation of the approved plan during both import and lost-ack reconciliation; copied-key and hostile-accessor behavior; wrong-database rejection; cloud-principal immutability; full encrypted value and timestamp preservation; exact source/target preimage drift; fence, admissions and immutable-trigger drift; missing AAD/graph evidence and dependent history; unique ID, slug and hash conflicts; actual blocking of concurrent source and fence writes; lost COMMIT acknowledgement with read-only reconciliation; and simultaneous same-plan attempts producing one receipt.

## Why production remains closed

The fixture intentionally does not implement the full Collect schema, actual RLS and permissions, real mutation and side-effect triggers, catalogue/function hashes, cross-database snapshot and fencing protocol, full FK and reference graph, encrypted-field inventory, real key/AAD compatibility, managed logging controls, or authoritative deployment and source-identity proofs. Its broad fixture table grants are unsuitable for production. Real collection inserts also encounter the application mutation fence and collection-title history trigger; these must not be disabled or bypassed by this experiment. A matching string, fixture evidence flag, empty fixture dependency table, or owner selection does not prove those real requirements.

A managed executor requires independently verified real source and target identities and catalogue/trigger manifests; an enforceable source/target writer fence and settled admissions held through the relevant transaction boundaries; complete dependency, original-attribution and object graph decisions; proven key/AAD compatibility and actual encrypted-value preservation; managed-role/RLS and operational logging review; a durable protected receipt and lost-ack protocol; and tested backup/recovery and reconciliation. Until these are designed and proved, this directory cannot execute against either real database and no current business rows have been migrated by it.
