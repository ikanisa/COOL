# SMS queue security and recovery — R4

BuriMunsi / M-Money • 9 November 2026

R4 adds an authenticated encrypted implementation of the R3 append-port contract and an independently anchored two-phase commit protocol. It preserves all R2/R3 shared policy sources, application classifiers, original fixtures, pinned dependencies and the host-only file adapter. No application worker, installed handset, production database or hosted service is changed.

## Implemented

| File | Responsibility |
|---|---|
| `EncryptedJournal.kt` | Versioned AES-GCM envelope, full-header authentication, configured owner/installation/generation/contract/store/key binding, provider-generated IV, strict length/version/sequence checks and lookup-only Android Keystore resolver. |
| `TrustedCheckpoint.kt` | Explicit immutable anchor and prepared/committed states; legal transition validation; trusted checkpoint and durable ciphertext transaction interfaces. No decrement, cancellation or automatic bootstrap transition exists. |
| `ProtectedJournalPort.kt` | Implements `AppendJournalPort`: verifies ciphertext against an independent anchor, decrypts and replays the full retained journal, prepares the next anchor, persists the encrypted journal, and commits the anchor before reporting COMMITTED. |
| `tests/protected/ProtectedChecks.kt` | Actual JVM AES-GCM tests plus synthetic in-memory durable-port fault injection, rollback, isolation, concurrent reservation and recovery tests. |
| `tests/python/test_protected_delivery.py` | Source preservation, additive R3 installation, repeat-install and verification-input coverage tests. |

The encrypted envelope uses `AES/GCM/NoPadding`, a 96-bit provider-generated IV and 128-bit authentication tag. The configured key must be provisioned as AES-256 by an approved provider. No key material is embedded, exported, generated or regenerated by shared runtime code. The existing-key resolver accepts an existing `SecretKey` handle, including a non-exportable Android Keystore key. The Android-specific lookup is compiled, not executed or qualified on a device in this delivery.

The cipher authenticates its complete header and binds ciphertext to the contract, owner, installation, generation, store identifier and configured key alias. Each seal initializes a new Cipher without a caller-provided IV. Tampered, truncated, wrong-key, cross-scope, wrong-version and wrong-sequence input is rejected. Authentication does not replace the independent rollback checkpoint.

## Commit and recovery rules

A normal append performs these operations in order:

1. Load a committed trusted checkpoint and its matching ciphertext. Authenticate, decrypt and replay the journal. Reject a checkpoint change observed while reading.
2. Compare the caller's original plaintext-journal hash. Validate that the proposed bytes append exactly one valid R3 record without removing or rewriting the existing history.
3. Encrypt the entire extended journal. CAS the checkpoint from committed old anchor to prepared old/new anchors. No upload effect is available.
4. Atomically and durably replace the encrypted blob using its previous ciphertext hash as the CAS precondition.
5. CAS the prepared checkpoint to the committed new anchor. Only this completed sequence can return COMMITTED to `CommitDriver`.

A failed/unknown checkpoint preparation never releases a send. Once preparation has committed, every non-committed ciphertext/finalization result is UNKNOWN; the code does not cancel the checkpoint or pretend the old state is current. Reads are blocked while a preparation is pending.

`recoverPrepared()` can finalize only the exact new ciphertext named in the pending anchor, after authentication, plaintext hash, record-count and journal validation. It returns a recovery status, not a network effect. A recovered in-flight reservation remains in flight: the original operation identifier and attempt history are retained. The existing queue restoration/retry policy still governs it.

When preparation succeeded but the new ciphertext never reached durable storage, recovery intentionally remains blocked. This is an availability trade-off, not an omitted automatic reset: accepting the old ciphertext here would also accept an attacker restoring that same old ciphertext. An explicit, separately authorized recovery workflow is required. Neither repeated calls nor a missing key cause recreation or evidence deletion.

## Critical production boundary

**The trusted checkpoint is a required external dependency, not a local file supplied by this package.** It must offer independently rollback-resistant, authenticated, durable, linearizable CAS and enforce `CheckpointRules` on the trusted side. A checkpoint stored beside the ciphertext, in SharedPreferences, in the same restorable database, or merely encrypted with another locally restored key does not meet that contract. A test deliberately demonstrates that restoring BOTH the checkpoint and ciphertext defeats detection; this limitation is not hidden.

No independently rollback-resistant checkpoint backend or production Android `CiphertextBlobPort` is implemented or deployed here. The new controller is executable and tested with synthetic ports; it is not a production durability claim. The existing R3 POSIX adapter is still plaintext, test-only, and excluded from mobile installation.

Checkpoint unavailability blocks this queue adapter. A production intake path therefore needs durable encrypted quarantine/intake before attempting queue admission, with no intake checkpoint advancement until evidence is retained. A remote checkpoint dependency must not cause an offline handset to discard incoming SMS. This atomic intake/quarantine integration remains open.

The full-journal rewrite is deliberately bounded by the R3 64 MiB/10,000-record limits, but it has O(journal size) work per commit and multiple transient memory copies. It is not a mobile throughput, memory or battery qualification. Managed-runtime buffers cannot promise total plaintext erasure; temporary arrays explicitly owned by the implementation are wiped where practical. No raw evidence or provider exception text is included in the adapter's status strings.

## Reproduce local checks

Prerequisites: Python 3.10+, Kotlin/JVM 1.9+, Java 17+, and POSIX for the inherited host filesystem suite. The runner uses local tools and vendored source; it downloads nothing.

```sh
cd SMS_Policies_R4
python3 scripts/verify.py --output /tmp/sms-policies-r4-verification
```

The output directory must not already exist. `evidence/verification.json` records measured test counts, exact input hashes, tool versions, compile/runtime exits and external gates. Exit 0 means local checks passed, not production acceptance. Missing tool prerequisites produce blocked/exit 2. `--require-external` also keeps the exit nonzero while external gates remain open.

## Additive source installation

```sh
python3 scripts/install_overlay.py --application burimunsi --target /path/to/native/burimunsi
python3 scripts/install_overlay.py --application mmoney --target /path/to/M-Money_Native_Android
# The commands above only inspect and plan. Add --apply for an authorized source installation.
```

The installer refuses edited or unknown core baselines, conflicting files and symlinks. Against an R3 installation it adds only the three shared Kotlin files listed above; every prior source stays unchanged. It does not configure Gradle, provision keys/checkpoints, perform a migration, install the plaintext host adapter, wire workers or enable upload. Tests exercise temporary repository fixtures, not the actual Collect checkout.

See `docs/R4_INTEGRATION.md` for the adapter contract and production gate sequence. The R3 documents and provenance remain historical references; R4 status is authoritative for this delivery. `TASK_STATUS.json` separates implementation, measured local verification and external acceptance.

Production Android encrypted blob transactions, key provisioning/rotation/invalidation handling, independent trusted checkpoint backend and authorization, explicit fresh-store provisioning, intake/quarantine/checkpoint atomicity, legacy queue migration without deletion of originals, worker/lifecycle-fence wiring, APK compilation/instrumentation and device storage durability, actual Collect integration, hosted/database idempotency, physical-carrier/SIM/reboot/replacement tests, and capacity/compaction qualification remain open.

## API references used

Official references consulted on 9 November 2026:

- Oracle Java SE 17 `Cipher`: https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/crypto/Cipher.html
- Android `KeyGenParameterSpec.Builder`: https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder
- Android Keystore system: https://developer.android.com/privacy-and-security/keystore

These support API/cryptographic integration choices, not native acceptance of this package. Java's Cipher documentation requires a distinct GCM IV for each encryption with a key and AAD before ciphertext. Android's randomized-encryption setting rejects caller-provided IVs for encryption; the shared implementation lets the provider generate them. Key strength and provider properties must be verified during explicit provisioning rather than by exporting key bytes.
